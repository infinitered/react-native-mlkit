# Phase 0 — Findings & chosen approach

**Feature:** experimental, opt-in **arm64 iOS Simulator** support for the
MLKit-backed packages (no Rosetta), addressing
[#259](https://github.com/infinitered/react-native-mlkit/issues/259).

This is the Phase 0 deliverable required by the task brief: explore, confirm,
and commit to an approach **before** writing any feature code. Nothing in this
document changes runtime behavior.

---

## 0. TL;DR / chosen approach

| Decision | Choice |
| --- | --- |
| Package that owns the feature | `@infinitered/react-native-mlkit-core` (every iOS feature pkg depends on it) |
| Opt-in surface (Expo) | **new** config plugin on each iOS feature package, prop `arm64SimulatorExperimental: true` |
| Opt-in surface (bare RN) | a pinned Ruby helper `require`d in the consumer's Podfile, gated on `RN_MLKIT_ARM64_SIM=1` |
| Podfile mechanism | `withDangerousMod(['ios','podfile'])` that injects a **minimal `require` + call** of the shipped Ruby helper into the existing `post_install` block (append, never clobber). There is **no** first-class AST Podfile modifier in `@expo/config-plugins` for SDK 56 — see §2. |
| Transform tool | a **pinned Ruby script** shipped in `core`, using only Xcode CLI tools (`lipo`, `vtool`, `otool`, `codesign`). No third-party packaging tool. |
| Framework kind | MLKit ships **static** frameworks (proven by the `(GMLImage.o)` archive-member notation in #259's linker error) — see §3. |
| Slice strategy | **Option A** — `ios-arm64` (pristine device) + `ios-arm64-simulator` (retagged). Documented Intel-Mac caveat. See §4. |
| Assembly | build a per-framework **`.xcframework`** into a git-ignored build dir; rewire only the **simulator** linkage to it; device slice stays the pristine Google binary. |

> ⚠️ **Environment limitation (must read).** Phase 0 was performed in a **Linux
> CI container with no Xcode toolchain** — `lipo`, `vtool`, `otool`, `codesign`,
> `pod`, `xcodebuild`, and `xcrun` are all absent, and there is no committed

## 1. Monorepo map & pod dependency graph

Yarn 3 workspaces + Turbo. Published packages live under `modules/`; the
ExampleApp (Expo SDK 56, managed) lives under `apps/ExampleApp`.

`@infinitered/react-native-mlkit-core` owns the shared iOS integration. Its
podspec depends on `MLKitVision`, and **every** iOS feature package depends on
`RNMLKitCore`, so `core` is the natural home for the shared transform logic.

Per-package Google MLKit pod dependencies (from the podspecs):

| Package | Direct Google MLKit pods |
| --- | --- |
| `react-native-mlkit-core` | `MLKitVision` |
| `react-native-mlkit-face-detection` | `GoogleMLKit/FaceDetection` |
| `react-native-mlkit-text-recognition` | `GoogleMLKit/TextRecognition` |
| `react-native-mlkit-image-labeling` | `MLKitImageLabeling`, `GoogleMLKit/ImageLabelingCustom` |
| `react-native-mlkit-object-detection` | `GoogleMLKit/ObjectDetection`, `GoogleMLKit/ObjectDetectionCustom` |
| `react-native-mlkit-document-scanner` | _(Android only — no iOS podspec)_ |

These resolve transitively to the fat-framework Google pods that lack an
`arm64-simulator` slice. Per #259 (Expo SDK 55 era) the transitive set
included at least:

- `MLImage` ← the framework named in the linker error
- `MLKitCommon`
- `MLKitVision`
- `MLKitFaceDetection`
- `GoogleMLKit/*` umbrella sub-specs
- `GoogleDataTransport`, `GoogleUtilities`, `GoogleUtilitiesComponents`,
  `GTMSessionFetcher`, `nanopb`, `PromisesObjC`, `Protobuf`/`GoogleToolboxForMac`
  (transitive Google deps; several also ship fat frameworks without an
  arm64-sim slice).

**Consequence for the implementation:** the hook must **discover** the affected
frameworks from what CocoaPods actually fetched under `Pods/`, not hardcode a
single name. The discovery rule: scan installed pod framework bundles, and for
each fat `.framework` whose binary has an `arm64` (device) slice **but no
`arm64` simulator-platform slice**, queue it for transform. This naturally
covers transitive Google deps and is resilient to MLKit version bumps adding or
removing pods.

## 2. Expo SDK version & the supported `post_install` mechanism

- Expo **SDK 56** (`expo@^56`, `react-native@0.85.3`, `react@19.2`); iOS
  deployment target 16.4 (`expo-build-properties` in `app.json`).
- **No config plugins exist anywhere in the repo today.** All native wiring is
  via Expo autolinking (`expo-module.config.json`). So this feature introduces
  net-new plugin infrastructure — it is *not* "a prop on an existing plugin."
- I checked for a first-class Podfile / `post_install` modifier as the brief
  requested. `@expo/config-plugins` (the SDK 56 line) exposes typed mods for
  `Info.plist`, entitlements, `AppDelegate`, `Podfile.properties.json`, etc.,
  but **no AST-level `post_install`/Podfile modifier**. The CocoaPods Podfile is
  Ruby; there is no structured representation to mutate. The supported,
  current mechanism is `withDangerousMod(config, ['ios', 'podfile', ...])`,
  which is exactly what first-party plugins like `expo-build-properties` use for
  Podfile edits.

  **How I'll keep the string surgery safe and minimal** (addresses the brief's
  "don't assume string-surgery is cleanest"): the dangerous mod will *not*
  embed the transform logic as a Ruby heredoc. Instead it:
  1. ensures a single `require_relative`/`require` line to the **pinned Ruby
     helper shipped in `core`** is present near the top of the Podfile, and
  2. ensures a single call to that helper is present **inside the existing
     `post_install do |installer|` block** that `expo prebuild` already
     generates (append a line; never define a second `post_install`, which
     would clobber React Native's).

  Both insertions are guarded by a sentinel marker comment so re-running
  `prebuild`/`pod install` is idempotent, and other plugins' `post_install`
  contributions are preserved. All real logic lives in the versioned Ruby file
  (shared verbatim with the Phase 4 bare-RN path), so the plugin is a thin,
  auditable shim.

## 3. Toolchain behavior & static-vs-dynamic

- **Static, not dynamic.** #259's linker error reads
  `Pods/MLImage/Frameworks/MLImage.framework/MLImage[arm64][2](GMLImage.o)`.
  The `(GMLImage.o)` archive-member suffix means the Mach-O inside the
  `.framework` is a **static archive** (`ar`-style), not a dylib. This is
  consistent with our podspecs' `s.static_framework = true`. It changes the
  assembly step: we operate on a static library, and `vtool` may need to be run
  per-object (`ar -t`/`ar -x` → `vtool` each `.o` → `ar -crs` repack) if it
  cannot retag the archive in one shot on the target Xcode. The script will
  detect archive-vs-dylib via `file`/`otool` and branch accordingly.
- **Retag mechanism.** Flip the load command to platform **7 (iOS Simulator)**:
  `vtool -arch arm64 -set-build-version 7 <minos> <sdk> -replace -output …`.
  The 2021 "arm64-to-sim" approach predates the current toolchain; the modern
  `vtool` equivalent is believed correct but **must be verified on the target
  Mac's Xcode** (cannot run here — §0). The script asserts success by
  re-reading `LC_BUILD_VERSION` with `otool -l` and erroring if the platform
  isn't `7`.
- **Why an `.xcframework`, not an in-place fat binary.** A single fat Mach-O
  cannot hold two `arm64` slices (lipo keys by arch → device-arm64 and
  sim-arm64 collide). Rewriting the `Pods/.../X.framework` binary in place would
  therefore force us to drop the device arm64 slice, which would **break device
  builds** — violating the #1 safety constraint. An `.xcframework` separates
  slices *by platform*: `ios-arm64` (pristine device) and
  `ios-arm64-simulator` (retagged). Device/Release builds keep linking the
  untouched Google binary; only the simulator slice is synthesized. This is the
  property that makes App Store / TestFlight builds provably unaffected.
- **`.bundle` resources.** MLKit model `.bundle`s come in two flavors:
  (a) bundles **inside** the `.framework` are copied wholesale when
  `xcodebuild -create-xcframework -framework X.framework` packages each slice;
  (b) bundles delivered as **separate pod resources** at the `Pods/` root are
  handled by CocoaPods' resource phases independently and are arch-agnostic, so
  they're unaffected. The script will assert the expected layout and carry
  framework-internal resources into each xcframework slice. Exact carry
  behavior must be confirmed on a Mac.

## 4. Slice strategy — chosen: **Option A**, with rationale

- **Option A (chosen):** emit `ios-arm64` (pristine device) +
  `ios-arm64-simulator` (one retag, no `lipo` merge of x86_64).
- **Option B:** additionally retain `x86_64` in the simulator slice (universal
  sim), so Intel Macs can also build the simulator with the flag on.

**Why A:** the entire purpose of the flag is *native Apple-Silicon* simulator
builds. Intel-Mac contributors already have a fully working simulator path
**today** — it's the default flag-off behavior (x86_64 sim, no Rosetta). So the
only cost of Option A — "Intel Macs can't build the sim with the flag on" — is
mitigated by "Intel users simply leave the flag off and lose nothing." That
keeps the transform to a single retag with the fewest moving parts, matching
the brief's "pick one, don't over-build" guidance. The Intel caveat will be
documented prominently, and Option B remains a clean future prop if demand
appears. (Per the brief: do **not** build both up front.)

## 5. Safety constraints — how the design satisfies each

1. **Default unchanged** — feature is dead code unless the prop/env var is set;
   flag-off `pod install` is byte-for-byte today's output (exclusion intact).
2. **Explicit opt-in** — Expo prop `arm64SimulatorExperimental` or
   `RN_MLKIT_ARM64_SIM=1`; never inferred.
3. **Simulator-only, build-time-only** — only the synthesized sim slice is
   touched; device linkage untouched; nothing committed/vendored/uploaded.
4. **Idempotent** — sentinel marker in generated xcframework + Podfile; second
   install is a no-op.
5. **Non-destructive to other hooks** — append a line into the existing
   `post_install`; never redefine it.
6. **Fail loud** — layout assertions error with the framework name + detected
   MLKit version if slices/paths differ from expectations.
7. **No new Google downloads** — operate only on what CocoaPods fetched.
8. **No global third-party tools** — pinned Ruby script, Xcode CLI tools only.
9. **Reversible & branch-isolated** — additive; generated artifacts under a
   git-ignored build dir; never committed.
